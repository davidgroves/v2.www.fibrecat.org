## A very brief introduction to SSH key authentication

Password logins send a secret to the server and hope nobody else has it.
[SSH](https://www.openssh.com/) key authentication works differently.

You generate a key pair: a **private key** you keep, and a **public key** you can give away.
You put the public key in [`~/.ssh/authorized_keys`](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT) on the server.
When you connect, the server challenges you to prove you hold the matching private key.
You never send the private key over the wire.
You send a signature that only the private key could have produced, and the public key can verify.

That is the whole idea.
If you want the mathematics behind public-key cryptography, [Wikipedia's overview](https://en.wikipedia.org/wiki/Public-key_cryptography) and the [OpenSSH manual pages](https://man.openbsd.org/ssh-keygen) are good starting points.
This post is about where that private key lives, and what happens when you stop treating it as a file you can copy.

## How passphrases help

A normal SSH private key is a file on disk.
Permissions (`0600`, owned by you) are the first line of defence.
A passphrase is the second: the file is encrypted at rest, and [OpenSSH](https://www.openssh.com/) only decrypts it when you unlock it.

That means someone who "just steals the file" — a backup dump, a stolen laptop disk, a careless `scp` of `~/.ssh` — does not automatically get a usable key.
Without the passphrase, the blob is junk.

But passphrases have a sharp limit.

If an attacker can copy your `~/.ssh` directory, they often already have enough access to steal more than the file.
Malware that can read your home directory can often also:

- watch keystrokes while you type the passphrase
- talk to your running [`ssh-agent`](https://man.openbsd.org/ssh-agent) and ask it to sign things
- scrape the unlocked key from process memory

So a passphrase is still worth having.
It raises the bar for opportunistic theft of cold files.
It is a weak defence against a live compromise of the machine that unlocks the key.

That is the gap hardware-backed keys try to close.

## How private key material can live in hardware

The shared goal across these approaches is the same: usable private key material should not appear as a normal file you can copy off the machine.
Apple calls its isolated key coprocessor the [Secure Enclave](https://support.apple.com/en-gb/guide/security/sec59b0b31ff/web).
[TPMs](https://en.wikipedia.org/wiki/Trusted_Platform_Module) and hardware tokens solve a similar problem in different ways.

Three common options for SSH:

### TPM 2.0

Most modern PCs already have a [TPM 2.0](https://en.wikipedia.org/wiki/Trusted_Platform_Module).
Tools such as [`ssh-tpm-agent`](https://github.com/Foxboron/ssh-tpm-agent) let you create SSH keys bound to that chip.

With the usual TPM-agent approach, a sealed blob (often a `.tpm` file) still lives on disk.
That blob is useless on any other machine.
The TPM is what can unwrap and use it.
The credential is device-bound: steal the file without the TPM, and you have nothing usable.

This is unrelated to [Secure Boot](https://en.wikipedia.org/wiki/UEFI#Secure_Boot).
Secure Boot checks that the firmware and bootloaders are signed before they run.
A TPM *can* record that boot path and seal secrets to it — that is how disk encryption schemes like BitLocker often work — but `ssh-tpm-agent` does not do that by default.
Your SSH key is bound to the chip, not to a particular Secure Boot or measured-boot state.
Turning Secure Boot on or off does not create or destroy the SSH credential, and you do not need Secure Boot for this setup.

### Apple's Secure Enclave

On Macs with a [Secure Enclave](https://support.apple.com/en-gb/guide/security/sec59b0b31ff/web) ([Apple Silicon](https://support.apple.com/en-gb/HT211814), and earlier [T2](https://support.apple.com/en-gb/guide/security/secf14b09800/web)-era machines), you can create keys that the enclave generates and never exports in plaintext.
Apps like [Secretive](https://github.com/maxgoedjen/secretive), or newer macOS [CryptoTokenKit](https://developer.apple.com/documentation/cryptotokenkit) / [`sc_auth`](https://keith.github.io/xcode-man-pages/sc_auth.8.html) flows, expose those keys to OpenSSH as an agent or provider.
Signing happens inside the enclave.
Your Mac gets signatures out; it does not get a copy of the private key to email to yourself "just in case".

### YubiKey (and similar tokens)

A [YubiKey](https://developers.yubico.com/SSH/) (or other [FIDO2](https://fidoalliance.org/fido2/) / [PIV](https://developers.yubico.com/PIV/) token) holds key material in the token itself.
OpenSSH's [`ed25519-sk` / `ecdsa-sk`](https://developers.yubico.com/SSH/Securing_SSH_with_FIDO2.html) key types are the straightforward path for many people: generate with [`ssh-keygen`](https://man.openbsd.org/ssh-keygen) `-t ed25519-sk`, touch the key when prompted, put the public half on the server.

The private material is bound to the token, not to a particular laptop.
You can move the YubiKey between machines.
What you cannot do is extract a copyable private key file from it.

## What the consequences are

You cannot meaningfully back up the private key.

There is no encrypted USB copy to stash in a safe.
There is no "restore from [Time Machine](https://support.apple.com/en-gb/HT201250) and keep the same key" for a true Secure Enclave identity.
If the laptop dies, or the YubiKey is destroyed, that particular private key is gone.

A "backup" in this world is organisational, not cryptographic:

- generate a key on each device (or each token) you trust
- authorise each public key on the servers that matter
- revoke a public key when a device is lost

Lose a device?
Remove its public key from `authorized_keys` (and from [GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account), [GitLab](https://docs.gitlab.com/user/ssh/), cloud consoles, and anywhere else you pasted it).
The other devices keep working.

## What the benefits are

By design, usable private key material stays inside the hardware that protects it.
A Secure Enclave key never leaves the chip as plaintext.
A YubiKey key stays on the token.
A TPM-sealed `.tpm` blob may sit on disk, but without that TPM it is worthless.

An attacker who steals a disk image does not get a portable `id_ed25519` they can use from a café laptop.
Malware that can read your filesystem still cannot `cat` a Secure Enclave key into a Discord webhook.

You still have to trust the local machine for *use* of the key — malware can often ask the agent or enclave to sign login challenges while you are unlocked and present.
Hardware does not make you immune to a fully compromised client.
It does remove the classic failure mode where the private key itself becomes a durable, copyable credential.

That trade is the whole point:

- worse at "clone this key forever as a backup"
- better at "stealing files should not steal my SSH identity"

For many people who already carry a YubiKey, or who live on a Mac with a Secure Enclave, or who have a TPM sitting unused under Linux, that is a trade worth making.

## HOW TO: Generate a key on Linux

Install [`ssh-tpm-agent`](https://github.com/Foxboron/ssh-tpm-agent) (packaged on some distros, or via Go), then create a TPM-sealed key:

```bash
# Install (one option; your distro may package it)
go install github.com/foxboron/ssh-tpm-agent/cmd/...@latest

# Create a key bound to this machine's TPM
ssh-tpm-keygen
```

That writes something like `~/.ssh/id_ecdsa.tpm` (sealed private key) and `~/.ssh/id_ecdsa.pub` (public key).
Copy the `.pub` file into `authorized_keys` on servers as usual.

## HOW TO: Generate a key on OSX

On a Mac with a [Secure Enclave](https://support.apple.com/en-gb/guide/security/sec59b0b31ff/web), create a non-exportable identity and export an OpenSSH handle for it:

```bash
# Non-exportable P-256 key in the Secure Enclave; Touch ID on use
sc_auth create-ctk-identity -l ssh -k p-256-ne -t bio

# Download the handle into ~/.ssh (not the private key itself)
cd ~/.ssh && ssh-keygen -K -w /usr/lib/ssh-keychain.dylib -N ""
```

You will get a public key file (and a small handle file) named after the label.
Install the `.pub` on your servers.

### A note on ed25519 on the Mac

The Secure Enclave cannot do [Ed25519](https://en.wikipedia.org/wiki/EdDSA#Ed25519).
Apple's hardware only supports [NIST P-256](https://en.wikipedia.org/wiki/Elliptic_Curve_Digital_Signature_Algorithm) elliptic curve keys for enclave-protected keys ([Apple's documentation](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)).
That is a hardware limit of the Secure Enclave, not an OpenSSH limitation.
So a Secure Enclave SSH key will be something like `sk-ecdsa-sha2-nistp256@openssh.com`, not `ed25519-sk`.
If you want Ed25519 in hardware on a Mac, use a [YubiKey](https://developers.yubico.com/SSH/) (or similar) instead.

## HOW TO: Generate a key with Yubikey

Plug the [YubiKey](https://developers.yubico.com/SSH/) in, then:

```bash
ssh-keygen -t ed25519-sk -O resident -O verify-required -f ~/.ssh/id_ed25519_sk
```

- `ed25519-sk` keeps the private key material on the token ([Yubico's FIDO2 SSH guide](https://developers.yubico.com/SSH/Securing_SSH_with_FIDO2.html))
- `resident` stores the key handle on the YubiKey so you can reload it on another machine with `ssh-keygen -K`
- `verify-required` requires user verification as well as a touch: a [FIDO2](https://fidoalliance.org/fido2/) PIN on most YubiKeys, or a fingerprint on the [YubiKey Bio Series](https://www.yubico.com/products/yubikey-bio-series/)

Copy `~/.ssh/id_ed25519_sk.pub` to your servers.

On macOS, Apple's built-in OpenSSH often lacks FIDO support.
Install OpenSSH from [Homebrew](https://brew.sh/) (`brew install openssh`) and put it first on your `PATH` if `ed25519-sk` is refused.

## HOW TO: Use a key on Linux

Point SSH at the TPM agent, then connect as normal:

```bash
ssh-tpm-agent --install-user-units
systemctl --user enable --now ssh-tpm-agent.socket

# In your shell profile, or for this session:
export SSH_AUTH_SOCK="$(ssh-tpm-agent --print-socket)"

ssh user@server.example.com
```

The agent loads `*.tpm` keys from `~/.ssh`.
You may be prompted for a PIN or passphrase if you set one at creation time.

## HOW TO: Use a key on OSX

Tell OpenSSH to use Apple's [Secure Enclave](https://support.apple.com/en-gb/guide/security/sec59b0b31ff/web) provider, then use the handle file:

```bash
export SSH_SK_PROVIDER=/usr/lib/ssh-keychain.dylib

ssh -i ~/.ssh/id_ecdsa_sk_rk_ssh user@server.example.com
```

(The exact handle filename depends on the label you chose with `sc_auth`; check `~/.ssh`.)

[Touch ID](https://support.apple.com/en-gb/HT207054) will prompt when the enclave signs.
You can put the `SSH_SK_PROVIDER` export in your shell profile so you do not have to set it every time.

## HOW TO: Use a key with Yubikey

With the YubiKey plugged in:

```bash
# If you still have the local key file from generation:
ssh -i ~/.ssh/id_ed25519_sk user@server.example.com

# On a new machine, reload resident keys from the token:
ssh-keygen -K
# or load them straight into the agent:
ssh-add -K

ssh user@server.example.com
```

You will need to touch the YubiKey.
If you used `verify-required`, you also need user verification: a FIDO2 PIN on most keys, or a fingerprint on a [YubiKey Bio](https://www.yubico.com/products/yubikey-bio-series/) (the PIN remains as a fallback if the fingerprint does not match).
No usable private key is copied off the token — only a handle that still needs the hardware present.
